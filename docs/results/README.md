# Results

One file per run, generated by `scripts/report_run.py` — never edited by hand, so the numbers here
always match what is on disk in `runs/`:

```bash
python scripts/report_run.py runs/<run> --out docs/results/<run>.md
```

`runs/` is gitignored and lives outside any worktree, so these reports are the committed record of
what happened. Each one carries the environment, the resolved config, checkpoint sizes and SHA-256
prefixes, the per-stage training curves and the full evaluation metrics.

The headline row for each run goes in [../experiment_log.md](../experiment_log.md); the
interpretation goes there too. This directory is the evidence, not the argument.

## How to read these reports

**Always check the skill score before the MAE.** Every report ends with a "Is the count signal
real?" table comparing the run's MAE against the best single constant prediction on the same
records. A sampler that ignores the prompt entirely still posts a finite MAE — the requested counts
are uniform on 1…10, so answering "5" to every prompt scores an MAE of exactly 2.5. Only the skill
score says whether anything was learned:

| skill | meaning |
|---|---|
| ≤ 0 | no better than answering one fixed number for every prompt |
| 0 to 0.1 | a correlation exists but the counts are badly calibrated |
| > 0.3 | the counted value genuinely tracks the request |

**Pearson r and skill measure different things.** `r` can be strongly positive while skill is zero,
which is exactly what the pre-checks found: the read-out ranks counts correctly but sits at the
wrong scale. Ranking without calibration does not produce correct images.

**Read the count-response table before anything else.** It gives the mean counted value for each
requested n, and the slope of one against the other. Three very different failures produce similar
MAEs and only this table separates them:

| pattern | slope | what it means |
|---|---|---|
| counted ≈ requested | ≈ 1.0 | the count is being followed |
| flat row | ≈ 0.0 | the prompt is ignored; whatever the MAE, nothing was learned |
| rises then flattens | 0 < s < 1 | tracks small counts, saturates at larger ones |

The third is the frozen baseline's signature on this generator, and the `bias` column shows where
it starts. A sampler is only doing its job if it lifts the slope toward 1 at the counts where the
baseline has flattened — improving the overall MAE while leaving the curve flat usually means it
has found the best constant, not the count.

**A trained run is only meaningful next to the frozen baseline** evaluated with the same counter.
The frozen model already produces *some* number of objects; the question is whether the sampler
moved that number toward what was asked for.
